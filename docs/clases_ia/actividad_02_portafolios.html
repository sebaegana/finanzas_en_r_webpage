Introducción: El Problema

Contexto: Tienes acceso a 5 activos financieros: SPY (S&P 500), EFA (mercados desarrollados), IJS (small-cap), EEM (mercados emergentes), AGG (bonos). Deseas construir un portafolio que maximice el retorno relativo al riesgo, pero no sabes qué pesos asignar a cada uno.

Pregunta central: - ¿Cuál es la combinación óptima de pesos? - ¿Cómo verificar que esa solución es realmente óptima? - ¿Cómo publicar ese resultado para que otros lo usen?

Tu rol: seguir un pipeline de datos completo: 1. Parte 1 — EDA: entender los datos y correlaciones entre activos 2. Parte 2 — Markowitz: calcular la frontera eficiente (solución analítica exacta) 3. Parte 3 — Simulación: generar miles de portafolios aleatorios para validar que Markowitz es realmente óptimo 4. Parte 4 — Comparación: ¿cuán buena es la nube simulada vs la frontera exacta? 5. Parte 5 — Servicing: publicar el resultado como tu propio proyecto de Quarto en GitHub Pages

En cada parte, verás dos enfoques: Manual (escribes cada línea de código) y Asistido con Claude Code (acelera 5-10x).

Parte 2 — Markowitz: Optimización de la Frontera Eficiente

¿Por qué Markowitz primero?

Markowitz es la solución óptima exacta (analítica). Entender cómo se resuelve es fundamental antes de aproximarla con simulación.

Enfoque Manual

Paso 1: Preparar datos y matriz de covarianza

portafolio_retornos <- read_csv("data/portafolio_retornos.csv")

retornos_matrix <- portafolio_retornos |>
  select(-fecha) |>
  as.matrix()

retornos_esperados <- colMeans(retornos_matrix)
cov_matrix <- cov(retornos_matrix)
tasa_libre_riesgo <- 0.02 / 12

Tiempo: ~5 minutos.

Paso 2: Formular el problema de Markowitz

La frontera eficiente resuelve:

\[\min_w \left[ w^T \Sigma w \right]\]

sujeto a: - \(w^T r = r_p\) (retorno objetivo) - \(\sum w_i = 1\) (pesos suman 1) - \(w_i \geq 0\) (long-only, sin venta corta)

Paso 3: Instalar quadprog y resolver

# install.packages("quadprog")
library(quadprog)

n_activos <- ncol(retornos_matrix)
retornos_objetivo <- seq(0.08, 0.20, length.out = 50) / 12  # mensuales

frontera_markowitz <- data.frame(
  retorno = numeric(length(retornos_objetivo)),
  volatilidad = numeric(length(retornos_objetivo)),
  pesos = matrix(NA, nrow = length(retornos_objetivo), ncol = n_activos)
)

for (i in seq_along(retornos_objetivo)) {
  r_obj <- retornos_objetivo[i]

  # Formulación quadprog
  H <- 2 * cov_matrix
  f <- rep(0, n_activos)

  # Restricciones: sum(w)=1, w'*r=r_obj, w>=0
  A <- cbind(
    rep(1, n_activos),          # suma = 1
    retornos_esperados,          # retorno objetivo
    diag(n_activos)              # w >= 0
  )

  b0 <- c(1, r_obj, rep(0, n_activos))

  resultado <- solve.QP(H, f, t(A), b0, meq = 2)

  w_opt <- resultado$solution
  vol_opt <- sqrt(t(w_opt) %*% cov_matrix %*% w_opt) * sqrt(12)

  frontera_markowitz$retorno[i] <- r_obj * 12
  frontera_markowitz$volatilidad[i] <- vol_opt
  frontera_markowitz$pesos[i, ] <- w_opt
}

# Identificar portafolio tangente (máx Sharpe)
frontera_markowitz$sharpe <- (frontera_markowitz$retorno - 0.02) / frontera_markowitz$volatilidad
idx_tangente <- which.max(frontera_markowitz$sharpe)
portafolio_tangente <- frontera_markowitz[idx_tangente, ]

Tiempo: ~20 minutos (comprensión de quadprog, debugging de restricciones).

Paso 4: Visualizar la frontera exacta

frontera_markowitz |>
  ggplot(aes(x = volatilidad, y = retorno)) +
  geom_line(size = 1.2, color = "darkred") +
  geom_point(data = portafolio_tangente, color = "red", size = 4) +
  theme_minimal() +
  labs(title = "Frontera Eficiente de Markowitz (Exacta)",
       x = "Volatilidad Anual (%)",
       y = "Retorno Anual Esperado (%)")

Tiempo: ~5 minutos.

Total Parte 2 Manual: ~30 minutos.

Parte 3 — Simulación: Aproximar la Frontera por Monte Carlo

¿Por qué simulación después de Markowitz?

Ahora que conoces la solución exacta, usamos simulación para validar: “¿qué tan buena es una aproximación por fuerza bruta?”

Enfoque Manual

Paso 1: Simular miles de portafolios aleatorios

set.seed(42)

n_sims <- 10000
n_activos <- ncol(retornos_matrix)

resultados_sim <- data.frame(
  retorno_anual = numeric(n_sims),
  volatilidad_anual = numeric(n_sims),
  sharpe_ratio = numeric(n_sims)
)

pesos_matrix <- matrix(NA, nrow = n_sims, ncol = n_activos)

for (i in 1:n_sims) {
  # Generar pesos aleatorios long-only
  w <- runif(n_activos)
  w <- w / sum(w)

  # Retorno esperado del portafolio
  ret_port <- sum(w * retornos_esperados) * 12

  # Volatilidad del portafolio
  vol_port <- sqrt(t(w) %*% cov_matrix %*% w) * sqrt(12)

  # Sharpe ratio
  sharpe <- (ret_port - 0.02) / vol_port

  resultados_sim$retorno_anual[i] <- ret_port
  resultados_sim$volatilidad_anual[i] <- vol_port
  resultados_sim$sharpe_ratio[i] <- sharpe
  pesos_matrix[i, ] <- w
}

# Mejor portafolio simulado
idx_mejor <- which.max(resultados_sim$sharpe_ratio)
mejor_sim <- resultados_sim[idx_mejor, ]
mejor_pesos_sim <- pesos_matrix[idx_mejor, ]

Tiempo: ~15 minutos.

Paso 2: Visualizar la nube

resultados_sim |>
  ggplot(aes(x = volatilidad_anual, y = retorno_anual, color = sharpe_ratio)) +
  geom_point(alpha = 0.5, size = 1) +
  scale_color_viridis_c(direction = 1) +
  geom_point(data = mejor_sim, color = "red", size = 4, shape = 21, stroke = 2) +
  theme_minimal() +
  labs(title = "Frontera Eficiente Simulada (10,000 portafolios)",
       x = "Volatilidad Anual (%)",
       y = "Retorno Anual Esperado (%)",
       color = "Sharpe Ratio")

Tiempo: ~10 minutos.

Análisis: ¿Qué Observas?

  1. La nube simulada toca la frontera roja? → Depende de N (10k no es suficiente)
  2. El mejor punto simulado ≠ tangente de Markowitz? → Normal, es una aproximación
  3. ¿Cuán lejano está el mejor simulado del tangente? → Mide la “brecha de optimización”

Cálculo de la brecha:

# Distancia euclidiana entre mejor simulado y tangente de Markowitz
brecha_retorno <- abs(mejor_sim$retorno_anual - portafolio_tangente$retorno[idx_tangente])
brecha_vol <- abs(mejor_sim$volatilidad_anual - portafolio_tangente$volatilidad[idx_tangente])
brecha_sharpe <- abs(mejor_sim$sharpe_ratio - portafolio_tangente$sharpe[idx_tangente])

cat("Brecha de optimización:\n")
cat("Retorno:", brecha_retorno, "\n")
cat("Volatilidad:", brecha_vol, "\n")
cat("Sharpe:", brecha_sharpe, "\n")
cat("\nConclusión: Con 10k simulaciones, el error es de ~",
    round(brecha_sharpe / portafolio_tangente$sharpe[idx_tangente] * 100, 2), "%\n")

Parte 5 — Servicing: Publicar tu Proyecto en GitHub Pages

¿Por qué servir importa?

Hasta aquí tienes un análisis que funciona en tu máquina. Servicing = convertir ese análisis en una página web interactiva que otros puedan usar sin ejecutar código.

La buena noticia: no necesitas servidor costoso ni configuración compleja. GitHub Pages + Quarto = gratis + automático.

El flujo completo (Crear Proyecto → GitHub Pages)

Paso 1: Preparar carpeta local con estructura de proyecto

Qué hacer: Crea una carpeta en tu computador para tu proyecto. Dentro de ella, debes organizar: - Una carpeta llamada data/ donde guardarás el archivo CSV de retornos - La carpeta raíz será donde vivirán tus archivos de Quarto (.qmd)

Por qué: Quarto necesita una estructura de directorios clara para saber dónde buscar datos y dónde generar la salida HTML.

Detalle: Descarga el archivo portafolio_retornos.csv desde la clase y colócalo dentro de data/. Este será el único archivo externo que necesitarás.

Paso 2: Crear configuración de Quarto

Qué hacer: Crea un archivo de configuración que le diga a Quarto cómo montar tu sitio web. Este archivo debe estar en la raíz de tu proyecto y debe especificar: - Que quieres crear un website (no solo un documento) - Dónde Quarto debe guardar los archivos HTML generados (en una carpeta llamada docs/) - El título de tu sitio - La estructura de navegación (qué páginas tendrá y en qué orden)

Por qué: Sin este archivo, Quarto no sabe que quieres un sitio web multi-página. Este archivo es el “cerebro” de tu proyecto.

Detalle: El archivo debe ser simple pero preciso. Quarto es muy sensible a la indentación y los nombres de carpetas.

Paso 3: Crear archivo principal con tu análisis

Qué hacer: Crea un archivo llamado index.qmd (el “home” de tu sitio) que contenga todo tu análisis: - Tu introducción y contexto del problema - Toda tu Parte 1 (EDA) con gráficos - Toda tu Parte 2 (Markowitz) con explicación matemática - Toda tu Parte 3 (Simulación) - Toda tu Parte 4 (Comparación) con gráficos overlay

Por qué: Este archivo es el corazón de tu proyecto. Quarto lo convertirá a HTML y lo servirá como tu página principal.

Detalle: El archivo debe incluir un encabezado (frontmatter) con metadatos: título, autor, fecha. Luego el contenido con encabezados, código R en bloques, y explicación en markdown.

Paso 4: Agregar interactividad con JavaScript

Qué hacer: En el mismo archivo index.qmd, agrega una sección nueva (Parte 5) con un bloque de JavaScript especial que: - Cargue tus datos CSV - Cree 5 sliders interactivos (uno para cada activo) - Calcule dinámicamente el retorno, volatilidad y Sharpe ratio cuando muevas los sliders - Muestre los resultados en una caja visual

Por qué: Esto convierte tu análisis estático en una herramienta interactiva que otros pueden usar sin abrir R. Los usuarios pueden experimentar con diferentes pesos y ver resultados en tiempo real.

Detalle: Esta es la única parte que requiere JavaScript (lenguaje de navegador). Quarto tiene un sistema especial llamado Observable que facilita escribir JS sin ser un experto. Los sliders deben estar normalizados para que siempre sumen 100%.

Paso 5: Convertir análisis a página HTML

Qué hacer: Desde tu terminal, ejecuta un comando que le diga a Quarto: - Procesa mi archivo index.qmd - Corre todo el código R - Genera gráficos - Convierte markdown a HTML - Guarda el resultado en la carpeta docs/

Por qué: El navegador no entiende .qmd. Necesitas convertirlo a HTML para que pueda ser visto en web.

Detalle: Este proceso toma 30-60 segundos (depende de cuántos cálculos tengas). Quarto genera una página completamente estática e independiente — no necesita servidor.

Paso 6: Crear repositorio en línea en GitHub

Qué hacer: Ve a github.com y crea un nuevo repositorio público. Debes: - Darle un nombre descriptivo (ej: portafolio-optimo-r) - Marcarlo como público (así otros pueden verlo) - NO inicializar con README (tú ya tienes archivos locales listos)

Por qué: GitHub es donde vivirá el código y los archivos HTML. Es el “servidor” que almacena tu proyecto y lo hace accesible.

Detalle: Después de crear, GitHub te dará una URL única para tu repositorio. Guárdala — la usarás en el próximo paso.

Paso 7: Sincronizar tu carpeta local con GitHub

Qué hacer: Desde tu terminal, dentro de tu carpeta de proyecto: - Dile a Git que voy a conectar esta carpeta con GitHub - Agrega todos tus archivos (.qmd, docs/, data/, configuración) - Haz un “commit” (guardar una versión) con mensaje descriptivo - Sube todo a GitHub (push)

Por qué: Esto vincula tu carpeta local con el repositorio en línea. A partir de ahora, cada vez que hagas cambios y hagas push, los cambios aparecerán en GitHub.

Detalle: Git controla el historial de cambios. El primer push llevará todos tus archivos. Los siguientes pushes solo subirán lo que cambió.

Paso 8: Activar despliegue automático en GitHub Pages

Qué hacer: En la página de tu repositorio en GitHub, ve a Settings → Pages y configura: - Especifica que quieres desplegar desde una rama (no desde acciones automatizadas) - Elige la rama main - Especifica que los archivos HTML están en la carpeta /docs - Guarda los cambios

Por qué: GitHub Pages es un servicio gratuito que toma los archivos HTML en docs/ y los sirve automáticamente en una URL pública. Esto es lo que hace tu página accesible en internet.

Detalle: Una vez activado, tu página estará disponible en https://[tu-usuario].github.io/[nombre-repo]/. GitHub Pages se actualiza automáticamente cada vez que haces push a la rama main.

Flujo de actualización futuro

Una vez que tu proyecto esté publicado, no necesitas volver a hacer estos 8 pasos. El flujo se simplifica:

  1. Modifica tu archivo index.qmd con cambios (más código, mejor análisis, correcciones)
  2. Renderiza localmente para probar que todo funciona
  3. Sube cambios a GitHub — GitHub Pages se actualiza automáticamente en ~30 segundos

Tu página pública refleja siempre la última versión que hayas subido a GitHub.

Troubleshooting Común

“Error: quarto render falla”

Posible causa: Faltan librerías de R.

# Instala las que faltan
Rscript -e "install.packages('tidyverse'); install.packages('quadprog')"

“GitHub Pages muestra 404”

Pasos a verificar:

  1. En tu repo, ve a Settings → Pages
  2. Confirma que Source es “Deploy from a branch” + “main” + “/docs”
  3. Espera 1-2 minutos (GitHub tarda en actualizar)
  4. La URL debe ser: https://[usuario].github.io/[repo-name]/

“Los sliders Observable no cargan datos”

Causa común: El archivo CSV no está en la ruta correcta.

datos = FileAttachment("portafolio_retornos.csv").csv()

// ✅ Correcto (asume que quarto render está en la raíz)
datos = FileAttachment("data/portafolio_retornos.csv").csv()

“La página renderiza pero los cálculos no funcionan”

Verifica:

  1. ¿El CSV se carga? Abre browser console (F12) y busca errores

  2. ¿Los valores son NaN? Revisa que los nombres de columnas coincidan:

    names(portafolio_retornos)  # En R

  3. ¿Falta variable en Observable? Usa console.log(variable) en {ojs}

“¿Cómo actualizar la página después de cambios?”

# 1. Modifica tu .qmd
# 2. Renderiza
quarto render

# 3. Commit + push
git add .
git commit -m "update: [descripción]"
git push origin main

# GitHub Pages se actualiza en ~30 segundos
# Recarga la página en tu navegador (Ctrl+Shift+R para forzar caché)

Reflexión Final: IA como Herramienta, No Reemplazo

✅ Usa IA para:

  • Boilerplate (cargas, transformaciones estándar)
  • Exploración de sintaxis (“¿cómo uso quadprog?”)
  • Debugging (“¿por qué falla esta restricción?”)
  • Observable JS (sintaxis compleja)
  • Documentación y comentarios

❌ NO uses IA para:

  • Decisiones de estrategia (tú eliges qué validar)
  • Validación de resultados (verifica siempre que Sharpe = (ret - rf) / vol)
  • Comprensión (entiende el código antes de publicarlo)
  • Pensar (IA acelera ejecución, no estrategia)

Alternativas y Extensiones

Si quieres explorar más allá…

Opción 1: Agregar una API con plumber (R)

En lugar de solo Observable JS estático, puedes crear un backend interactivo:

# En R: instala.packages("plumber")
# Crea un archivo api.R con endpoints que reciban pesos
# y devuelvan retorno/volatilidad calculados

#* @post /calcular-portafolio
function(pesos) {
  retorno <- sum(pesos * retornos_medios)
  return(list(retorno = retorno))
}

Luego desplégalo en Shinyapps.io o Heroku (gratuitamente).

Tiempo adicional: ~60 min de aprendizaje.

Opción 2: Usar Shiny en lugar de Observable JS

Si prefieres R puro, puedes usar library(shiny) en lugar de Observable JS:

library(shiny)

ui <- fluidPage(
  sliderInput("peso_spy", "SPY (%)", 0, 100, 20),
  textOutput("resultado")
)

server <- function(input, output) {
  output$resultado <- renderText({
    paste("Retorno:", input$peso_spy * 0.12)
  })
}

shinyApp(ui, server)

Deploy a shinyapps.io automáticamente.

Nota: Shiny tiene servidor gratuito limitado (25 horas/mes).

Opción 3: Versión en Python con Streamlit

Si prefieren Python en lugar de R:

import streamlit as st
import pandas as pd

peso_spy = st.slider("SPY (%)", 0, 100, 20)
st.write(f"Retorno estimado: {peso_spy * 0.12}%")

Deploy en Streamlit Cloud (gratis).

Tiempo adicional: ~45 min si ya conoces Python.
